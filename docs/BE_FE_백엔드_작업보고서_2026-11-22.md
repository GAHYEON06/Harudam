# 하루담 BE 백엔드 구현과 FE 호환성 조사 보고서

작성일은 2026년 11월 22일입니다. GitHub `GAHYEON06/Harudam`의 최신 BE를 기준으로 기존 Firebase 구조를 유지하며 `parsePlaces`를 추가했습니다. FE는 읽기만 했으며 병합하지 않았습니다. 로컬 Firebase CRUD·보안 규칙 검증과 파서 단위 검증을 수행했습니다. 실제 네이버 공개 페이지는 접근 제한을 반환하여 실제 링크 추출 성공은 확인하지 못했습니다.

기존 `harudam-integration` 폴더에는 원격에 반영되지 않은 별도 로컬 작업이 있어 재사용하지 않았습니다. 최신 원격 BE에서 새로 시작했습니다. FE는 `git fetch origin FE`와 `git show FETCH_HEAD:경로`로 읽었고 FE 체크아웃·수정·커밋·푸시·머지는 수행하지 않았습니다.

GitHub 비교 화면의 FE 변경 8개 파일은 공통 조상 이후 FE가 바꾼 파일입니다. 두 브랜치 최신 트리의 직접 비교는 34개 파일 차이였으며 BE에만 있는 백엔드 파일 등이 FE 쪽에서는 없는 것으로 표시됩니다. 이를 삭제 요구로 해석하거나 FE를 통째로 병합하면 BE 기능을 잃을 수 있어 필요한 인터페이스만 반영했습니다.

| MainActivity.kt | 상태 표시줄과 화면 가장자리 표시 설정 | 백엔드 데이터 변경 불필요 |
| LoginScrenn.kt 및 SignupScreen.kt | UI·상태 전달 수정 | 기존 Firebase 인증 흐름 유지 |

FE의 URL 검증은 `naver.com` 및 모든 하위 도메인까지 넓게 허용하지만, 서버는 지도·플레이스에 필요한 정확한 호스트만 허용합니다. 서버가 임의 URL을 대신 요청하는 것을 막기 위한 호환성 조건입니다.

FE 분류 `음식·카페`는 `FOOD`, `관광`은 `TOUR`로 매핑합니다. BE의 `STAY`, `OTHER`도 유지합니다. FE의 표시 날짜는 `yyyy.MM.dd` 또는 월·일 문자열이지만 저장 API는 기존 `YYYY-MM-DD`를 유지해야 합니다. 날짜별 순서는 기존 `visitOrder` 1부터 시작하고 재정렬 때 해당 날짜의 모든 장소 ID를 중복 없이 보냅니다.

## 구현 기능

요청당 최대 10개, URL당 최대 500자를 받고 결과 순서를 유지합니다. 중복된 원본 URL은 한 요청 안에서 재조회하지 않습니다. 네이버 단축 링크 이동은 최대 4회 허용하며 매 이동마다 호스트를 재검증합니다. 외부 호스트·자격 증명 포함 URL·비표준 포트·HTTP 이외의 프로토콜을 거부하고 HTTP 공유 링크는 HTTPS로 요청합니다.

네트워크 동시 요청은 최대 2개, 배치 전체 제한은 20초, 페이지 본문 제한은 1 MiB입니다. HTTP 429는 `PROVIDER_RATE_LIMITED`로 구분합니다. 이름·주소·분류·좌표·원본 URL을 기존 저장 필드에 맞춰 반환하며 주소·좌표·분류 누락은 경고로 표시합니다. 모든 성공 결과는 사용자 확인이 필요합니다. 존재하지 않는 이름·주소·좌표나 예시 장소를 자동으로 만들지 않습니다.

반환된 `place`에는 저장 ID가 없으며 `addPlace` 또는 `createTrip`에서 기존 로직으로 생성합니다. 방문 날짜·순서·시간은 null, 메모는 빈 문자열로 반환하고 일정 지정은 기존 API가 담당합니다. 외부 네트워크 요청은 Firestore 트랜잭션 밖에서 처리합니다.

| 검증 | 결과 및 범위 |

| 최종 통합 실행 | 종료 코드 0, 20개 검증 묶음 통과. 합성 HTML의 파싱 결과를 기존 addPlace로 저장하고 getTrip으로 이름·주소·분류·원본 URL·좌표 일치 확인 포함 |
| 문법과 변경 검사 | node --check 및 git diff --check 통과 |
| 실제 공개 네이버 링크 | map.naver.com/p/entry/place/13572738은 HTTP 200이나 장소 메타데이터 없는 화면 틀. 모바일·PC 플레이스에서 HTTP 429 확인. 최종 파서는 PROVIDER_RATE_LIMITED 반환 |

단위 테스트의 HTML과 통합 테스트의 성공 추출 입력은 합성 fixture입니다. 실제 네이버 추출 성공을 의미하지 않습니다. Firebase 테스트는 `demo-harudam-parser` 프로젝트의 로컬 Auth·Functions·Firestore를 사용했고 운영 데이터는 사용하지 않았습니다.

초기 검증은 로컬 Node.js 24에서 실행했고, 최종적으로 배포 대상과 같은 Node.js 22.23.5에서도 파서 15개와 Firebase 통합 20개 검증 묶음이 모두 통과했습니다. 통합 실행 로그의 `Using node@22 from host`와 종료 코드 0을 확인했습니다. 배포 설정은 기존 `nodejs22`를 유지합니다.

## 최종 확인 기록

- 모든 소스와 문서 변경은 BE에서 커밋했습니다. FE에서 가져온 커밋을 병합하지 않았습니다.
- 푸시 전 원격 BE는 시작 커밋 `23cb69900cfbab3097f93060c33da0c6f1b045b6`, FE는 조사 커밋 `e443dfd051f2fc9e213e9aff45dba4ef318a3af1` 그대로였습니다.
- 변경 파일은 백엔드 코드·테스트·문서 8개입니다. Android 소스와 Firestore Rules의 차이는 없습니다.
- 운영 Firebase 배포와 FE 화면 수정은 수행하지 않았습니다. GitHub 반영 커밋은 이 보고서를 포함한 BE 커밋에서 확인할 수 있습니다.

## 미완료 항목과 운영 적용 조건

1. 실제 네이버 링크에서 이름·주소·좌표 추출 성공은 접근 제한 때문에 확인하지 못했습니다. 제공자가 공개 메타데이터를 주지 않으면 오류 또는 일부 필드 누락이 발생합니다. 원본 링크와 직접 입력한 장소 저장을 계속 지원해야 합니다.
2. 네이버 저장 목록 URL 하나에서 여러 장소를 가져오는 기능은 미구현입니다. 이번 복수 파싱은 여러 개의 개별 장소 URL을 받는 의미입니다.
3. 카카오맵·구글맵 파서는 미구현입니다.
4. FE의 예시 장소를 parsePlaces 응답으로 교체하고 여행 생성·목록·드래그 순서를 실제 API에 연결하는 작업은 남아 있습니다. FE 읽기 전용 요청에 따라 수정하지 않았습니다.
5. 운영 Firebase 배포는 수행하지 않았습니다. 저장소 기존 문서의 Spark 제한 설명은 과거 기록이며 이번에 요금제나 배포 상태를 새로 확인하지 않았습니다.
6. Android 빌드·화면·실기기 시험은 이번 백엔드 작업 범위에서 수행하지 않았습니다.

API 요청·응답·오류·저장 연결 방법과 재현 명령은 [parsePlaces API 사용 안내](PARSE_PLACES_API.md)에 정리했습니다.
